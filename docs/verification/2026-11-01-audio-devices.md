## Live output check

The throwaway driver is `/tmp/syrup-audio-probe/OutputProbe.swift`. It compiles the production controller and actor with `swiftc -swift-version 6 -O`. It captures the original volume, awaits `lower()`, verifies exact Float32 readback, awaits `restore()`, and verifies exact original readback. A defer directly resets and rechecks the original volume before removing the disposable defaults suite. The test changes only output volume.

Five fresh processes each ran seven lower/restore pairs. All 35 retained measurement pairs report exact lower and restore readbacks. Each process also reports an exact final direct reset. The output device was `BuiltInSpeakerDevice`, using virtual main volume. The original value was `0.74802697`, the lowered value was `0.2244081`, and the restored value was `0.74802697`.

Raw timings are in `2026-11-01-audio-device-timings.tsv`. The original detailed readbacks are at `/tmp/syrup-audio-output-repeat.log`. The timed region includes the actor hop, CoreAudio calls, and synchronized defaults persistence. It excludes the independent correctness readbacks and compiler startup. This is a device-operation measurement, not a dictation speedup or end-to-end latency result. The machine was busy, with load averages of 49.85, 21.91, and 17.14 on 14 logical CPUs when first checked. These timings do not establish a general latency bound. OutputDucker runs on its own actor, keeping the synchronous device and defaults calls off the main actor.

An initial UID lookup used the wrong CoreAudio data contract and failed with `!siz`. The SDK header documents a CFString qualifier and AudioDeviceID result. The corrected controller uses that contract. One subsequent early probe reported a readback mismatch, but its buffered values were lost when an uncaught top-level error terminated it. The driver now catches errors so diagnostics survive. The next baseline check and all retained subsequent checks confirmed the original volume. The mismatch did not recur and its cause remains unproven. An additional earlier seven-pair successful check is excluded from the table.

Real per-channel fallback hardware, device removal during a write, a real process crash during lowering, and a physical closed lid remain unverified. Fake-controller tests cover per-channel volume, partial write failure, persisted recovery across actor instances, default-device changes, missing devices, user changes, and repeated operations. The full test log includes existing macOS linkd and simulator-version diagnostics, with a successful macOS test result.

## Integration API

Create one `OutputDucker` for the app. Call `try await ducker.restoreAfterCrash()` once at launch. When the raw bool `settings.lowerOtherAudioWhileRecording` is enabled, call `try await ducker.lower()` at recording start. Call `try await ducker.restore()` on stop, cancellation, or failure. No-op restores are safe. Handle `OutputVolumeError` at the owning app boundary. Failed restores retain their record for retry.

The pipeline and settings UI are outside this verification scope. AppState changed only to map the closed-lid input error.
